# SPEC-hub-orchestration

한 줄 요약: 허브 세션이 그룹의 워크트리·세션을 자율 관리하고, Feature·Loop·Manual 프리셋과 Pi 하네스의 Goal·List·Loop·Audit·TODO·에이전트 대화·에이전트 질문, 채팅 @참조가 어떻게 동작하는지 확정한다.

관련 문서: [[30-specs/SPEC-graph-pi-ade]], [[orca-cli-and-pi-sessions]], [[00-meta/glossary]]

## 목적

기존 ADE는 세션을 관찰·제어하지만, 그룹 단위 작업을 에이전트가 스스로 나누고 분배하고 통합하는 규칙이 없다. 사용자가 첫 프롬프트 하나를 던지면 허브 세션이 필요한 워크트리와 하위 세션을 만들고, 부족한 결정을 사용자에게 묻고, 세션 사이의 결과를 중계해 작업을 끝까지 진행하도록 한다.

동시에 Pi 하네스 패키지가 Goal·List·Loop·Audit·TODO·에이전트 대화·에이전트 질문을 제공해, 사용자가 앱에서 그룹의 진행 상황·감사 결과·답변 대기 상태를 볼 수 있게 한다.

## 대상 사용자

자기 PC에서 Orca로 여러 레포지토리의 Pi 세션을 돌리는 1인 사용자. 그룹을 만들고 첫 프롬프트를 던진 뒤, 허브가 만든 구조를 보드에서 확인하고 질문에 답하는 사람이다. 조직 공유·다중 사용자 권한은 다루지 않는다.

## 포함 범위

- 허브 세션의 그룹 내 자율 관리 권한과 그 결과가 앱에 반영되는 방식.
- Feature·Loop·Manual 프리셋의 생성 시점 동작, 첫 프롬프트 필수 여부, 프리셋별 플레이스홀더.
- Feature 프리셋의 명세 질문 → 워크트리·세션 생성 → 목업 선택 → API 중계 흐름.
- Loop 프리셋의 레포지토리×검토 축 워크트리 생성 → 역할별 loop → 종료 시 허브 통합 → 재시작 흐름.
- Manual 프리셋의 허브 자율 구조 결정.
- Pi 하네스 패키지가 제공하는 Goal·List·Loop·Audit·TODO·에이전트 대화·에이전트 질문.
- Goal 완료 주장 시 새 Audit 세션을 만들고, 읽기 전용 검사 후 verdict를 남기는 흐름.
- 허브 List 항목의 fan-out, 하위 Goal 부모 링크, 하위 Audit 결과 롤업.
- 앱의 Goal·List·Loop·Audit 인스펙터 탭, TODO 인스펙터, 보드 4슬롯 배지, 에이전트 질문 카드·채팅 인라인·대기 세션 강조, 에이전트 메시지 표시.
- 채팅 @참조의 프로젝트·브랜치·워크트리·파일·폴더 지정과 없는 워크트리의 확인 후 생성.

## 제외 범위

- 허브의 그룹 생성·삭제·그룹 필드 편집. 그룹은 사용자가 앱에서 만든다.
- 그룹 전체 에이전트 대화, 하위 세션끼리의 직접 대화, 사용자의 에이전트 스레드 참여. 지금은 허브와 하위 세션 사이만 허용한다.
- 앱에서 TODO를 추가·수정·완료·삭제하는 조작. 앱은 읽기 전용이다.
- 앱에서 Goal·List·Loop·Audit을 만들거나 바꾸는 조작. 시작·중지·재시도·재배정·검증은 Pi 명령이나 에이전트 도구로 한다.
- 기존 GLLA 패키지를 그대로 연동하는 것. 같은 개념을 새 하네스에 구현한다.
- 사용자가 앱에서 Audit verdict를 뒤집는 조작. 앱은 결과를 표시만 한다.
- 프리셋을 그룹 데이터에 저장하는 것. 프리셋은 생성 시점의 초기 지시로만 쓴다.
- @로 없는 프로젝트(레포지토리)나 없는 파일·폴더를 만드는 것. 워크트리와 브랜치만 확인 후 만들 수 있다.
- OS 알림, 소리, 외부 메신저 전송.
- 하네스 패키지의 구현 구조·저장 형식·IPC·배포 방식. 설계 단계에서 정한다.
- Loop의 최대 회차·시간·토큰 기본값, 정체(plateau) 판정, 측정 명령 안전 정책의 확정 값. 아래 미정사항에 남긴다.
- Manual 플레이스홀더의 최종 문구. 아래 미정사항에 남긴다.

## 사용 흐름

### 1. 그룹 생성과 프리셋

1. 사용자가 `그룹 추가`를 연다.
2. 그룹 이름, 프리셋(Feature·Loop·Manual), 부모 저장소, 모델, 첫 프롬프트를 입력한다. 프리셋을 바꾸면 첫 프롬프트의 플레이스홀더가 그 프리셋의 예시로 바뀐다.
3. Feature·Loop는 첫 프롬프트가 필수다. 비어 있으면 생성 버튼이 비활성이고 이유를 보여준다. Manual은 비워도 만들 수 있다.
4. 생성하면 그룹과 허브 세션 1개가 만들어진다. 워크트리는 만들지 않는다. 허브 세션은 부모 저장소 폴더에서 시작한다.
5. 앱은 프리셋 지시와 첫 프롬프트를 허브 세션의 초기 컨텍스트로 보낸다. 프리셋 지시는 그룹 데이터에 저장하지 않는다.
6. 첫 프롬프트가 없는 Manual 그룹은 허브가 사용자의 입력을 기다린다. 이후 허브는 모든 프리셋에서 Manual과 같이 자율 관리한다.

| 프리셋 | 첫 프롬프트 | 플레이스홀더 예시 |
| --- | --- | --- |
| Feature | 필수 | `예: 로그인·회원가입 기능과 채팅 로직을 백엔드에서 구현하고, 프론트엔드 디자인은 여러 목업 시안을 만든 뒤 나에게 선택을 요청해. 선택한 목업을 프론트엔드에 적용해.` |
| Loop | 필수 | `예: 이 프로젝트의 보안과 속도, 코드의 확장성과 유지보수성을 검토해.` |
| Manual | 선택 | `예: 이 그룹에서 진행할 작업을 설명해.` (문구 미정) |

### 2. Feature 프리셋

Feature는 레포지토리별 기능 구현과 디자인·API 중계가 섞인 요청을 허브가 순서대로 푸는 흐름이다. 아래는 두 레포지토리 예시이며, 허브는 요청에 필요한 레포지토리·워크트리만 만든다.

1. 사용자가 Feature 그룹을 만들고 첫 프롬프트로 "로그인·회원가입과 채팅 로직은 백엔드에서 구현하고, 프론트엔드는 여러 목업 시안을 만든 뒤 나에게 선택을 요청하고, 선택한 목업을 적용해"를 보낸다.
2. 허브는 요청을 레포지토리별 작업과 선행 결정으로 나눈다. 백엔드에서 구현할 범위, 인증 방식, 데이터 필드, API 계약처럼 사용자만 정할 수 있는 제품 결정이 요청에 없으면 에이전트 질문으로 사용자에게 묻고 답을 기다린다. API 계약의 구현 수준 세부(엔드포인트·필드명·오류 코드)는 백엔드 세션이 정하고, 허브가 프론트엔드에 중계한다.
3. 답을 반영해 백엔드 레포지토리에 워크트리를 만들고, 그 워크트리에 세션을 만든 뒤 확정된 명세와 구현 프롬프트를 **그 세션의 Goal로** 보낸다.
4. 프론트엔드 레포지토리에 워크트리를 만들고 세션을 만든 뒤, 여러 목업 시안을 만들고 사용자에게 선택을 요청하라는 프롬프트를 **그 세션의 Goal로** 보낸다.
5. 프론트엔드 세션의 질문이 앱에 뜨고 그 세션이 `질문 대기`로 강조된다. 사용자가 시안을 고르면 답이 프론트엔드 세션으로 전달되고 세션이 선택대로 작업을 이어간다.
6. 프론트엔드가 백엔드 API를 알아야 하면 프론트엔드 세션이 허브에 에이전트 메시지로 묻는다. 허브는 백엔드 세션이 확정한 API 계약(엔드포인트·요청·응답·오류)을 프론트엔드 세션에 전달하고, 그 대화는 프론트엔드와 허브 채팅에 남는다.
7. 허브는 진행 상황을 그룹 TODO와 세션 TODO로 관리하고, 각 Goal 완료는 Audit으로 검증한 뒤 통합 결과를 사용자에게 보고한다.

이 흐름의 각 작업 단위는 하위 세션의 Goal이며, 허브는 하위 Goal이 Audit 승인을 받아야 다음 List 항목을 배정한다. 허브 자신도 Goal을 갖고, 그 Goal은 하위 세션의 작업을 오케스트레이션해 완료한다. 자세한 규칙은 §10에서 정한다.

허브는 API 계약이 필요한 연동 작업을 시작하기 전에 그 계약을 확정한다. 목업·디자인처럼 API와 독립적인 작업은 먼저 시작할 수 있다. 워크트리 이름과 브랜치는 허브가 요청에서 정하며, 정확한 작명 규칙은 미정이다.

### 3. Loop 프리셋

Loop는 레포지토리마다 같은 검토 축을 병렬로 돌리고, 각 세션의 Goal·Loop를 감사·통합하는 흐름이다. 여기서 **loop**는 한 Goal을 측정값 또는 Audit 기준으로 반복하는 실행 단위, **회차**는 loop의 1회 반복, **주기**는 허브가 현재 List 항목의 하위 Goal을 모두 승인받아 통합하고 다음 항목으로 넘어가는 단위다.

1. 사용자가 Loop 그룹을 만들고 첫 프롬프트로 "이 프로젝트의 보안과 속도, 코드의 확장성과 유지보수성을 검토해"를 보낸다.
2. 허브는 요청을 레포지토리×검토 축으로 나눈다. 예를 들어 프론트엔드에 `fix/perf`·`fix/security`·`fix/architecture`, 백엔드에도 같은 세 축의 워크트리를 만든다.
3. 허브는 이번 검토 주기의 범위를 하나의 List 항목으로 만들고, 그 항목을 6개 워크트리 세션에 fan-out한다. 배정받은 세션은 Goal과 Loop를 만들고, 역할의 고정 프롬프트와 측정값·상한 설정을 받는다.
4. 각 세션은 분석 → 수정 → 검증 → 보고를 loop로 반복한다. 하네스가 회차마다 측정값을 기록하고, loop는 측정 목표 달성·Audit 승인·최대 회차/시간/토큰 도달·중지 중 하나로 끝난다.
5. Goal 완료를 주장하면 Audit 세션이 읽기 전용으로 검증한다. 승인되면 Goal은 `complete`가 되고, 거부되면 Goal은 `active`로 돌아가 상한 안에서 loop를 계속한다.
6. 각 하위 Goal이 승인될 때마다 허브가 그 결과를 통합한다. 변경을 검토하고, 축 사이의 충돌·중복을 조정하고, 공유 명세와 TODO를 갱신한다. 통합의 git 의미(병합 대상 브랜치·순서·충돌 처리·push 여부)는 미정이다.
7. 현재 List 항목의 유효 하위 Goal이 모두 승인되어야 허브는 다음 항목(다음 검토 주기)을 배정한다. 대체되지 않은 `aborted`가 있으면 항목은 `차단`으로 남고, 재시도·재배정·범위 수정으로만 푼다.
8. 모든 항목이 끝나면 허브는 자신의 Goal을 Audit에 올린다. 승인되면 완료, 거부되면 남은 항목이나 범위를 조정한다. 허브가 Loop를 쓰면 이 오케스트레이션 주기를 반복한다.
9. 사용자는 보드에서 각 세션의 Goal·Loop·Audit 상태와 허브 항목의 진행을 보고, 질문이 오면 답한다.

Loop의 최대 회차·시간·토큰 기본값, 정체(plateau) 판정, 사용자 조정 가능 여부는 미정이다. 그룹 전체 주기의 상한·종료 조건·중지 수단도 미정이다. 확정 전에는 허브가 하위 세션에 설정을 전달하고 앱이 그 설정을 표시하는 안을 기본으로 검토한다.

### 4. Manual 프리셋

1. 사용자가 Manual 그룹을 만든다. 첫 프롬프트는 선택이다.
2. 첫 프롬프트가 있으면 허브가 읽고, 없으면 입력을 기다린다.
3. 허브는 Feature·Loop의 구조를 참고해 요청에 맞는 구조를 스스로 정한다. 레포지토리별로 나눌지, 워크트리와 세션을 몇 개 만들지, Goal·List·Loop·Audit을 어떻게 쓸지, 어떤 질문이 필요한지를 판단한다.
4. 허브는 정한 구조대로 워크트리·세션을 만들고, 하위 세션에 Goal을 배정하며, 그룹을 자율 관리한다.
5. 사용자 결정이 필요하면 에이전트 질문을 쓰고, 하위 세션과의 협업은 에이전트 메시지로 한다. 각 Goal의 완료는 Audit으로 검증한다.

Manual에는 프리셋 지시가 없다. 허브의 판단이 곧 그룹 구조다.

### 5. 허브의 자율 관리

| 대상 | 허브 권한 | 사용자 확인 |
| --- | --- | --- |
| 워크트리 | 생성, 이름 변경, 부모 변경, 삭제 | 없음 |
| 세션 | 생성, 프롬프트 전송, 중단, 삭제 | 없음 |
| TODO | 그룹 TODO·세션 TODO 생성, 수정, 완료 | 없음 |
| Goal·List | 자신의 Goal·List 생성, 하위 세션에 Goal 배정, 진행·감사 상태 조회 | 없음 |
| Loop | 하위 Goal의 Loop 설정 전달, 중지 요청 | 없음 |
| Audit | 완료 주장 시 Audit 세션 생성 요청, 하위 verdict 롤업 | 없음 |
| 사용자 질문 | 에이전트 질문 생성 | 질문 자체는 사용자 답변을 기다림 |
| 그룹 | 생성·삭제·그룹 필드 편집 불가 | 해당 없음 |

- 허브의 관리 조작은 사용자 확인을 받지 않는다. 앱에서 사용자가 직접 하는 삭제 확인과 다르다.
- 이 표의 '삭제'는 워크트리·세션 삭제를 뜻한다. 병합·push·미커밋 변경이 있는 워크트리 삭제는 포함하지 않으며 미정이다.
- 기존 ADE의 사용자 수동 워크트리·세션 생성·삭제 경로는 이번 명세에서 제거하지 않는다. 허브와 사용자가 같은 그룹을 동시에 관리할 때의 우선순위는 미정이다.
- 허브가 만든·바꾼·지운 결과는 보드, 사이드바, 인스펙터에 반영된다.
- 허브는 그룹의 모든 워크트리와 세션을 대상으로 관리할 수 있다.
- 허브의 Goal은 직접 구현이 아니라 하위 세션의 Goal을 오케스트레이션해 완료한다. 허브 List 항목은 여러 하위 Goal로 fan-out할 수 있고, 유효 하위 Goal이 모두 승인되어야 다음 항목으로 넘어간다.
- 워크트리를 삭제할 때 그 안의 세션을 어떻게 처리하는지는 미정이다. 확정 전에는 삭제 전에 그 워크트리의 세션 목록을 허브 채팅에 남긴다.

### 6. TODO

TODO는 에이전트가 작업을 잊지 않고 사용자에게 진행을 보여주기 위한 목록이다. 앱은 표시만 한다.

TODO는 Goal과 별개다. Goal은 완료 조건을 가진 결과 단위이고, TODO는 그 Goal을 수행하기 위한 실행 작업 목록이다. 둘을 자동으로 동기화하지 않는다.

- **그룹 TODO**: 그룹 전체에 걸친 작업. 그룹의 모든 세션이 읽고, 허브와 그룹의 하위 세션이 추가·수정·완료할 수 있다.
- **세션 TODO**: 한 세션의 작업. 그 세션과 허브만 읽고 추가·수정·완료할 수 있다.
- 상태는 `할 일`, `진행 중`, `완료` 세 가지다.
- 앱은 상태보드 우측 인스펙터에 TODO를 표시한다. 그룹이나 허브를 선택하면 그룹 TODO를, 세션을 선택하면 그 세션의 세션 TODO와 그 아래 그룹 TODO를 보여준다.
- 항목은 제목, 상태, 만든 세션, 마지막 갱신 시각을 보여준다.
- 앱에는 추가·수정·완료·삭제 버튼이 없다. 체크박스도 조작할 수 없다.
- TODO가 없으면 `TODO 없음`을 보여준다.
- 앱을 다시 열어도 TODO는 유지된다. 앱 화면이 갱신되면 에이전트의 변경이 반영된다.

### 7. 에이전트 대화

에이전트 대화는 하위 세션이 허브에 작업을 묻거나, 허브가 하위 세션에 결과·명세를 전달하는 통로다.

- 지금은 허브와 하위 세션 사이만 허용한다. 하위 세션끼리 직접 대화하거나 그룹 전체에 보내는 것은 지원하지 않는다.
- 보낸 세션과 받은 세션의 채팅 모두에 메시지가 남는다. 사용자 메시지와 구분되는 `에이전트` 라벨과 보낸 세션 이름을 붙이고, 시간순으로 표시한다.
- 사용자는 이 대화를 읽을 수 있지만 그 스레드에 직접 참여하지는 않는다.
- 받는 세션이 실행 중이 아니면 앱이 그 세션을 자동으로 재개해 메시지를 전달한다. 자동 재개에 실패하면 메시지를 보관하고 보낸 세션에 실패를 알린다. 보관된 메시지는 받는 세션이 다시 실행될 때 전달한다.
- 받는 세션이 삭제됐으면 전달하지 않고 보낸 세션에 실패를 알린다.
- 메시지는 텍스트만 다룬다. 파일 첨부는 이번 범위가 아니다.

### 8. 에이전트 질문

에이전트 질문은 세션이 사용자에게 결정을 요청하고, 답이 올 때까지 기다리는 기능이다.

- Pi의 `ask_user_question`과 같은 형식을 따른다. 한 번에 질문 1~4개, 각 질문에 선택지 2~4개와 자유 입력을 둘 수 있고, 다중 선택이 필요한 질문은 다중 선택으로 표시한다.
- 질문이 오면 세션은 `질문 대기` 상태가 되고 답변 전까지 다음 작업을 진행하지 않는다. `질문 대기`는 Pi 세션의 저장 상태가 아니라 앱이 표시하는 대기 플래그다.
- 앱은 인스펙터 상단에 질문 카드를 띄우고, 같은 질문을 그 세션의 채팅에도 인라인으로 표시한다.
- 보드의 세션 카드와 사이드바의 세션 행에는 `질문 대기` 배지를 붙이고 강조한다. 정확한 색·테두리·애니메이션은 미정이다.
- 사용자는 카드나 채팅 인라인 어느 쪽에서 답해도 된다. 답이 제출되면 두 곳의 표시가 함께 갱신되고 세션이 이어서 진행한다.
- 한 번의 질문 묶음에 여러 질문이 있으면 카드에 모두 표시하고 한 번에 제출한다. 세션이 질문 묶음을 연속으로 보내면 먼저 온 묶음부터 처리하고 나머지는 대기열에 둔다.
- 앱을 닫았다 다시 열어도 답하지 않은 질문과 강조는 유지된다.
- 답변 전에 세션이 삭제되면 질문은 취소되고 활성 카드에서 사라진다. 채팅 기록에는 남긴다.
- 답변을 받은 세션이 중지돼 있으면 답변을 보관하고, 세션을 재개해 전달한다. 재개에 실패하면 답변을 보관하고 사용자에게 알린다.

### 9. 채팅 @참조

채팅 입력에서 `@`를 입력하면 현재 그룹의 프로젝트·브랜치·워크트리·파일·폴더를 참조할 수 있다.

#### 9.1 입력과 후보

1. `@`를 입력하면 입력창 아래에 현재 그룹의 프로젝트 후보가 뜬다. 계속 입력하면 후보가 필터링된다.
2. `@backend`처럼 프로젝트를 고르면 후보 패널에 `프로젝트`, `브런치`, `워크트리` 선택이 뜬다.
3. `프로젝트`를 고르면 그 프로젝트 참조가 입력창에 들어간다.
4. `브런치`를 고르면 그 프로젝트의 브랜치 목록이 뜨고, 고른 브랜치 참조가 들어간다. 브랜치는 기존 것만 고를 수 있다.
5. `워크트리`를 고르면 그 프로젝트의 워크트리 목록이 뜬다. 워크트리가 없으면 만들 브랜치를 고르거나 새 브랜치 이름을 입력하는 확인 팝업을 띄우고, 확인하면 브랜치와 워크트리를 만든 뒤 참조를 넣는다. 취소하면 태그를 해석하지 못한 상태로 두고 전송을 막는다.
6. 워크트리 참조 뒤에 `/`를 입력하면 그 워크트리 기준으로 파일·폴더 경로 자동완성이 뜬다. 고른 경로가 참조로 들어간다.
7. 파일·폴더 참조는 워크트리 참조 뒤에서만 제공한다. 프로젝트나 브랜치만 고른 상태에서는 경로 자동완성을 제공하지 않는다.

#### 9.2 직접 입력과 해석

| 입력 예 | 해석 | 대상이 없을 때 |
| --- | --- | --- |
| `@backend` | `backend` 프로젝트 | 프로젝트 목록에 없으면 오류이며 만들지 않는다. |
| `@backend/feature/security` | `backend`의 워크트리 `feature/security`. 워크트리가 없으면 같은 이름의 브랜치. | 워크트리와 브랜치가 모두 없으면 확인 후 브랜치·워크트리를 만든다. |
| `@backend/feature/security/src/auth.ts` | 그 워크트리의 파일 `src/auth.ts` | 파일이 없으면 오류이며 만들지 않는다. |
| `@backend/feature/security/src/auth/` | 그 워크트리의 폴더 `src/auth/` | 폴더가 없으면 오류이며 만들지 않는다. |

- 같은 이름의 워크트리와 브랜치가 모두 있으면 워크트리를 먼저 참조한다.
- 워크트리가 없는 브랜치에는 파일·폴더 참조를 붙일 수 없다. 경로 자동완성도 워크트리가 있을 때만 뜬다.
- 직접 입력한 경로도 같은 규칙으로 해석한다. 후보 패널은 입력을 돕는 수단이며, 해석 규칙은 동일하다.
- 확인 팝업에는 만들 레포지토리·브랜치·워크트리 위치를 보여준다. 정확한 문구와 배치는 미정이다.
- 워크트리 생성은 워크트리만 만들고 세션은 만들지 않는다. 세션은 허브나 사용자가 따로 만든다.
- 워크트리 생성에 실패하면 태그를 해석하지 못한 상태로 두고, 오류를 보여주며 전송을 막는다.
- 해석하지 못한 태그가 하나라도 있으면 메시지를 보내지 않는다. 태그를 지우거나 대상을 고친 뒤 보낸다.

#### 9.3 전송

- 태그가 붙은 메시지를 보내면 앱은 참조 대상을 해석해 레포지토리·브랜치·워크트리·파일·폴더 정보를 세션 프롬프트에 함께 넣는다.
- 메시지에는 태그가 그대로 남아 사용자가 어떤 대상을 가리켰는지 읽을 수 있다.
- 한 메시지에 여러 태그를 넣을 수 있다.

### 10. Goal·List·Loop·Audit

Goal·List·Loop·Audit은 세션의 작업을 결과 단위로 관리하고, 반복 실행과 완료 감사를 분리하는 Pi 하네스 기능이다. TODO가 실행 작업 목록이라면 Goal은 완료 조건을 가진 결과 단위다. 앱은 이 기능들을 인스펙터에서 읽기 전용으로 보여준다.

#### 10.1 Goal

- 모든 작업 세션은 활성 Goal 하나와 대기 Goal 목록을 가진다. 허브는 최상위 Goal 하나와 그 Goal이 소유하는 List를 가지며, 허브의 Goal은 직접 구현이 아니라 하위 세션의 Goal을 오케스트레이션해 완료한다.
- Goal은 목표, 완료 조건 1개 이상, 상태, 소유 세션, 선택적 부모 허브 List 항목, 선택적 Loop, Audit 이력을 가진다.
- 상태는 `active`, `auditing`, `complete`, `paused`, `aborted`다. 화면 라벨은 진행, 감사 중, 완료, 일시정지, 중단이다.
- `complete`는 Audit 승인으로만 된다. `aborted`는 종료 상태다.
- 허브 Goal은 그룹의 List 전체를 소유하는 최상위 Goal이다. 허브 List 항목은 Goal이 아니며, 허브 Goal의 완료 조건은 "모든 항목 완료 + 통합 기록 존재 + 원래 목표의 요구가 하위 결과에 매핑됨"이다. 모든 항목이 완료되고 통합 기록이 남으면 허브 에이전트가 허브 Goal의 완료를 주장한다.
- 완료 조건이 없으면 Goal을 만들 수 없고, 완료를 주장할 수 없다.
- 완료를 주장하면 Goal이 `auditing`이 되고 Audit 세션이 만들어진다. 감사 중에는 소유 세션이 새 작업을 시작하지 않는다. Audit 승인 → `complete`; 거부 → `active`로 돌아가고 실패한 완료 조건을 표시; 불가능 → `aborted`; 감사 인프라 오류 → verdict가 아니며 `paused`와 오류를 표시한다. 오류 재시도 정책은 미정이다.
- Audit 거부 후 다시 완료를 주장하려면 이전 Audit 이후 최소 1회의 작업과 증거 갱신이 있어야 한다. Goal당 Audit 시도 횟수 상한은 설정값이며 기본값은 미정이다.
- 질문 대기 중에는 Goal이 `paused`이고 앱은 `질문 대기` 플래그를 함께 표시한다. 답변 후 `active`로 돌아간다. `paused`에는 사유(`user`, `agent`, `audit_error`, `question`, `loop_bounds`, `dependency`, `standby`)를 남긴다.
- 완료 조건이 바뀌면 revision을 올리고, 이전 revision의 Audit 승인은 현재 Goal에 유효하지 않다.
- Goal 생성·완료 주장·일시정지·재개는 에이전트 도구와 Pi 명령으로 한다. 앱은 만들거나 바꾸지 않는다.

#### 10.2 List

- 세션 List는 세션별 Goal 큐다. 세션 List의 각 항목은 Goal이며, 목표와 완료 조건을 가진다. 세션은 활성 Goal 하나와 대기 항목을 가진다.
- Audit 승인으로 Goal이 `complete`가 되면 다음 대기 항목을 자동으로 활성화한다. `aborted`된 Goal은 자동으로 다음 항목으로 넘어가지 않고 List를 멈춘다. 사용자나 에이전트가 재시도·다음 항목 선택을 한다.
- List는 일시정지할 수 있다. 일시정지 중에는 새 Goal을 활성화하지 않고 큐에만 넣는다.
- 허브의 List는 오케스트레이션 큐다. 항목은 세션이 아니라 완료해야 할 결과 단위이며, 한 항목을 여러 하위 세션에 fan-out할 수 있다. **허브 List 항목은 Goal이 아니다.** 허브 Goal 하나가 List 전체를 소유하고, 항목은 그 Goal 아래의 작업 묶음이다. 세션 List 항목만 Goal이다.
- 허브는 항목을 배정할 때 하위 세션에 Goal 생성을 요청한다. 하위 세션은 그 Goal을 자기 List에 넣고, 유휴면 자동 활성화한다. 하위 List가 일시정지면 큐에 넣고 기다린다.
- 허브는 현재 항목의 유효 하위 Goal이 모두 승인되어야 다음 항목을 배정한다. 허브 List를 한 번에 모두 처리하지 않는다.
- 허브 항목에 배정된 하위 Goal이 하나도 없으면 그 항목은 완료될 수 없다. 허브가 그 항목의 마지막 하위 Goal 배정을 마치면 `childGoalIds`를 고정하고, 그 시점의 유효 하위 Goal 집합으로 완료를 판정한다.
- 하위 Goal이 `aborted`면 그 항목은 `차단`으로 남고 다음 항목으로 넘어가지 않는다. 재시도는 새 Goal을 만들고 이전 Goal을 `supersededByGoalId`로 대체한다. 대체된 Goal은 유효 집합에서 빠지며, 유효 하위 Goal이 모두 승인되어야 차단이 풀린다.
- 항목은 유효 하위 Goal이 모두 승인되고 허브 통합 기록이 남으면 완료로 표시한다. 완료된 뒤 하위 Goal의 revision이 바뀌어도 완료는 되돌리지 않고, 새 작업은 새 항목으로 만든다. 항목에는 `completedAt`과 `completedRevision`을 고정한다.
- 허브 List 항목의 표시 상태는 대기·진행·차단·완료다. 저장 상태는 `queued`/`active`이고 차단·완료는 유효 하위 Goal에서 파생한다.
- 하위 Goal은 부모 허브 List 항목 ID를 저장한다. 허브 Goal은 모든 항목의 완료와 통합 기록을 완료 조건으로 삼고, 허브 Audit이 하위 verdict와 완료 조건 결과를 롤업한다.
- 완료·중단된 Goal과 Audit 이력은 아카이브에 남는다. List 탭에서 `아카이브` 필터로 본다. 세션을 삭제해도 그룹 아카이브의 기록은 유지한다.

#### 10.3 Loop

- Loop는 한 Goal을 측정값 또는 Audit 기준으로 반복하는 실행 단위다. Goal 하나에 Loop 하나를 붙일 수 있다.
- Loop는 목표 측정값, 측정 명령, 방향(min/max), 현재값·최고값, 회차·최대 회차, 시간·토큰 상한, 상태, 종료 이유, 측정 이력을 가진다.
- 측정값은 선택이다. 측정값이 없으면 Audit 승인이 유일한 품질 기준이고, 상한은 그대로 적용한다. 보안처럼 수치화가 약한 작업은 이 방식을 쓴다.
- 하네스가 매 회차 후 측정 명령을 실행해 값을 기록한다. 에이전트의 자기 보고를 측정값으로 쓰지 않는다.
- Loop는 측정 목표 달성, Audit 승인, 최대 회차·시간·토큰 도달, 사용자·에이전트 중지 중 하나로 끝난다.
- 측정 목표에 도달하면 실행을 멈추고 완료를 주장한다. Loop는 `paused`(`pauseKind=audit`, `stopReason=metric_target`)가 되고, Audit 승인 후 `done`이 된다.
- 상태는 `running`, `paused`, `stopped`, `done`이다. `paused`는 사용자·에이전트 일시정지, 감사 대기, 오류, 의존성 대기를 포함하고 `pauseKind`로 구분한다. `done`은 Goal이 Audit 승인된 경우, `stopped`는 상한 도달·불가능·사용자·에이전트 중지로 재개하지 않는 경우다.
- Audit이 거부되면 Goal은 `active`로 돌아가고, 상한이 남아 있으면 Loop를 `running`으로 재개한다. 상한이 이미 소진됐으면 Loop는 `stopped`, Goal은 `paused`(`pauseKind=loop_bounds`)로 두고 사용자·허브의 범위 조정을 기다린다.
- 상한 도달·사용자 중지로 Loop가 `stopped`되면 Goal은 `active`로 남기지 않고 `paused`로 둔다. 아무도 일하지 않는 Goal이 진행 중으로 보이지 않게 한다.
- Loop가 없는 Goal은 Audit 거부 후 최소 1회의 작업·증거 갱신 없이 다시 완료를 주장할 수 없다. 연속 거부 횟수 상한은 설정값이며 기본값은 미정이다.
- Loop의 상한 기본값, 정체(plateau) 판정, 측정 명령의 안전 정책은 미정이다.

#### 10.4 Audit

- Audit은 Goal 완료 주장 시 새 Audit 세션에서 수행한다. 작업 세션과 분리된 감사 세션이며, 작업 에이전트가 자기 결과를 승인하지 않는다.
- Audit 세션은 대상 Goal의 워크트리를 읽기 전용으로 검사한다. 파일, 채팅, 도구 출력, 테스트 결과, 완료 조건별 증거를 읽고 verdict를 쓴다. 소스·설정·의존성을 수정하는 쓰기 도구는 비활성이다. 테스트·측정 명령은 실행할 수 있지만, 그 산출물은 증거로만 쓰고 커밋하지 않는다.
- 감사 시작 시 대상 워크트리의 커밋 해시와 상태를 고정한다. 감사 중 워크트리가 바뀌면 verdict를 쓰지 않고 `error`로 끝내고 다시 감사한다.
- Goal이 `auditing`이면 소유 세션은 새 작업을 시작하지 않는다. 질문 답변·메시지 수신처럼 상태를 바꾸지 않는 동작만 허용한다.
- 허브 Goal의 Audit 세션은 롤업 감사다. 허브 채팅, 모든 하위 Goal의 verdict·증거 요약, 통합 기록을 읽고, 필요하면 하위 워크트리를 읽기 전용으로 연다. 코드를 새로 검사하는 감사가 아니라 "원래 목표의 각 요구가 하위 결과에 매핑되고, 모든 항목이 승인됐는가"를 판정한다.
- 완료 조건마다 증거가 있어야 한다. 증거가 없거나 조건을 충족하지 못하면 승인하지 않는다.
- verdict는 `approved`, `rejected`, `impossible`, `error`다. `error`는 verdict가 아니라 감사 인프라 실패다.
- 승인 → Goal `complete`, Loop `done`. 세션 Goal이면 List 다음 항목을 자동 진행하고, 허브 Goal이면 오케스트레이션을 끝낸다. 거부 → Goal `active`, 실패 조건 표시, Loop가 있으면 상한 내에서 계속. 허브 Goal 거부 → 보완 항목을 허브 List에 만들고 계속한다. 불가능 → Goal `aborted`. 하위 Goal 불가능 → 부모 허브 항목 `차단`; 허브 Goal 불가능 → 그룹 차단. 오류 → Goal `paused`, Loop `paused`(`error`), 오류 표시, 재시도 정책 미정.
- Audit 세션은 보드·사이드바에 임시 Audit 카드로 보인다. 진행, 채팅, verdict를 볼 수 있고, verdict가 끝나면 카드는 사라지고 Audit 이력에 남는다.
- Audit 이력은 최신 verdict와 이전 이력을 모두 보관한다. 각 항목은 verdict, 완료 조건별 통과/실패, 증거 요약, 실패 항목, 시각, 소요 시간, 모델을 보여준다. 감사 세션의 채팅·증거는 아카이브에서 다시 열 수 있다.
- 허브 Audit은 하위 Goal의 verdict를 증거로 롤업한다. 완료 조건에 필수 하위 Goal의 승인이 포함돼 있으면, 하나라도 미승인일 때 허브 Goal을 승인하지 않는다.

#### 10.5 앱 표시

- 인스펙터에 `Goal`·`List`·`Loop`·`Audit` 4탭의 감독 카드를 둔다. 그룹을 선택하면 허브의 4탭과 하위 세션 집계(진행·감사 중·질문 대기·차단·승인)를 함께 보여준다. 세션을 선택하면 그 세션의 4탭을 보여준다.
- Goal 탭: 목표, 상태, 완료 조건과 통과 여부, 부모 허브 항목, Loop 요약, 최신 Audit.
- List 탭: 활성 Goal, 대기 항목, 허브 항목의 fan-out과 하위 Goal 상태, 일시정지, 아카이브.
- Loop 탭: 측정 목표·현재값·최고값, 회차/최대, 시간·토큰 사용량, 상태, 종료 이유, 측정 이력.
- Audit 탭: 최신 verdict, 완료 조건별 결과, 증거 요약, 실패 항목, 이력, 아카이브.
- 보드 카드와 사이드바 세션 행에 4슬롯 배지를 둔다. Goal 상태 점, Loop 회차/진행 링, Audit 경고, List 대기 수. 카드 테두리·강조는 가장 심각한 상태를 따른다: 감사 거부·불가능·오류 > 일시정지·차단 > 질문 대기 > 진행·감사 중 > 완료 > idle.
- 감사 중에는 Audit 카드가 추가되고, verdict 후 사라진다. 카드가 사라져도 이력은 남는다.
- 앱은 Goal·List·Loop·Audit을 만들거나 바꾸지 않는다. 사용자는 Pi 채팅에서 자연어로 시작·중지·재시도·재배정·검증을 요청하고, 앱에는 그 버튼이 없다.
- Goal이 `paused`이면 사유(사용자 중지, 감사 오류, 질문 대기, Loop 상한, 의존성, 대기)를 함께 표시한다.
- 각 탭의 빈 상태는 `Goal 없음`, `List 비어 있음`, `Loop 없음`, `Audit 없음`이다.
- 기존 오케스트레이션 Run의 `goal`은 화면에서 `목적`으로 표기해 새 Goal과 구분한다. 데이터 필드는 당장 바꾸지 않는다.

### 11. Pi 하네스 패키지

하네스 기능은 이 저장소의 워크스페이스 패키지로 둔다. 앱과 함께 버전을 관리하고, 앱이 설치·실행을 관리한다. 패키지 이름·경로·배포 방식은 미정이다.

패키지는 앱이 실행하는 모든 Pi 세션(허브·하위·Audit)에 로드되고 다음 도구를 제공한다.

- **Goal 도구**: Goal 생성·완료 주장·일시정지·재개·조회, 완료 조건과 부모 항목 관리.
- **List 도구**: 큐 추가·활성화·일시정지·조회, 아카이브 조회.
- **Loop 도구**: 시작·일시정지·중지·측정·조회, 상한과 종료 이유 관리.
- **Audit 도구**: 감사 요청, verdict 기록, 이력 조회. Audit 세션 생성은 패키지가 담당한다.
- **TODO 도구**: 그룹 TODO·세션 TODO의 생성, 수정, 완료, 목록 조회.
- **에이전트 대화 도구**: 허브 또는 하위 세션에 메시지 전송, 받은 메시지 목록 조회.
- **에이전트 질문 도구**: 사용자에게 질문 묶음을 보내고 답변을 받을 때까지 대기, 답변 반환.

패키지는 앱이 읽을 수 있는 형태로 Goal·List·Loop·Audit·TODO·메시지·질문 상태를 남긴다. 저장 형식과 앱 연동 방식은 설계 단계에서 정한다.

Audit 세션은 읽기 전용 도구만 받는다. 감사 세션이 파일을 수정하거나 Goal 상태를 승인하는 도구를 직접 호출하지 못하게 한다. verdict 기록은 패키지가 감사 결과 채널로만 받는다.

패키지가 없거나 앱이 기대하는 버전과 맞지 않으면 앱은 안내를 보여주고 Goal·List·Loop·Audit·TODO·에이전트 대화·에이전트 질문 기능을 비활성화한다. 채팅과 @참조는 앱 기능이므로 계속 동작한다.

| 상황 | 기대 동작 | 사용자에게 보이는 메시지 |
| --- | --- | --- |
| Feature·Loop 그룹 생성 시 첫 프롬프트가 비어 있음 | 생성 버튼 비활성, 이유 표시 | `이 프리셋은 첫 프롬프트가 필요합니다.` |
| Manual 그룹 생성 시 첫 프롬프트가 비어 있음 | 그룹과 허브 세션 생성, 허브는 입력 대기 | `첫 프롬프트를 입력하면 허브가 작업을 시작합니다.` |
| 허브가 워크트리·세션을 생성·변경·삭제함 | 확인 없이 수행, 보드에 반영 | 없음 |
| 허브가 워크트리를 삭제함 | 워크트리를 보드에서 제거. 하위 세션 처리 방식은 미정 | 없음 |
| 완료 조건 없이 Goal을 만들려 함 | Goal 생성을 거부하고 완료 조건 입력을 요구 | `Goal을 만들려면 완료 조건이 하나 이상 필요합니다.` |
| 활성 Goal 없이 완료를 주장함 | 주장을 거부하고 활성 Goal 생성을 안내 | `완료를 주장할 활성 Goal이 없습니다.` |
| Audit 세션을 시작하지 못함 | Goal을 `paused`로 두고 오류 표시 | `Audit 세션을 시작하지 못했습니다. Goal을 일시정지했습니다.` |
| Audit이 완료 조건을 거부함 | Goal `active`, 실패 조건 표시, 상한 내 Loop 계속 | `Audit이 완료 조건을 승인하지 않았습니다. 실패 항목을 확인하세요.` |
| Audit이 불가능하다고 판정함 | Goal `aborted`. 하위 Goal이면 부모 허브 항목 `차단`, 허브 Goal이면 그룹 차단 | `이 Goal은 현재 조건으로 완료할 수 없다고 Audit이 판정했습니다.` |
| Audit 중 인프라 오류가 남 | verdict로 쓰지 않고 Goal `paused`, 오류 표시 | `감사 중 오류가 발생했습니다. 재시도 정책을 확인하세요.` |
| 하위 Goal이 `aborted`됨 | 허브 항목을 `차단`으로 두고 다음 항목을 막음. 재시도는 새 Goal로 대체하고 이전 Goal을 `supersededByGoalId`로 표시 | `하위 Goal이 중단되어 허브 항목이 차단되었습니다. 재시도하거나 재배정하세요.` |
| 허브 항목에 하위 Goal이 없음 | 항목을 완료로 만들지 않고 차단 표시 | `이 허브 항목에는 배정된 하위 Goal이 없습니다.` |
| 유효 하위 Goal이 모두 승인되지 않았는데 다음 항목을 배정하려 함 | 배정을 막고 남은 Goal 상태를 표시 | `현재 허브 항목의 유효 하위 Goal이 모두 승인되지 않아 다음 항목을 시작할 수 없습니다.` |
| 하위 List가 일시정지 상태임 | Goal을 큐에 넣고 재개를 기다림 | `하위 List가 일시정지 상태입니다. 재개하면 Goal이 시작됩니다.` |
| Loop가 상한에 도달함 | Loop `stopped`, Goal `paused`(`loop_bounds`), 범위 조정·재시작·중단을 안내 | `Loop 상한에 도달했습니다. 범위를 조정하거나 완료를 주장하세요.` |
| 감사 중 워크트리가 바뀜 | verdict를 쓰지 않고 Audit `error`, Goal `paused`, 재감사 | `감사 중 워크트리가 변경되었습니다. 다시 감사합니다.` |
| 감사 중 소유 세션이 새 작업을 시작함 | 새 작업을 거부하고 감사 완료를 기다림 | `감사 중에는 새 작업을 시작할 수 없습니다.` |
| 허브 Goal Audit이 거부됨 | Goal `active`, 보완 항목을 허브 List에 만들고 계속 | `허브 목표가 승인되지 않아 보완 항목을 만들었습니다.` |
| Goal당 Audit 시도 상한에 도달함 | Goal `paused`(`blocked`), 사용자·허브 판단 대기 | `Audit 시도 상한에 도달했습니다. 범위를 조정하거나 중단하세요.` |
| Loop 없는 Goal이 작업 없이 다시 완료를 주장함 | 재주장을 거부하고 작업·증거 갱신을 요구 | `감사 거부 후에는 작업과 증거를 갱신해야 다시 주장할 수 있습니다.` |
| Audit 세션이 쓰기 도구를 호출함 | 호출을 거부하고 읽기 전용임을 알림 | `Audit 세션은 읽기 전용입니다.` |
| 아카이브를 불러오지 못함 | 마지막으로 읽은 목록 유지, 오류 표시 | `아카이브를 불러오지 못했습니다.` |
| 에이전트 질문이 도착함 | 세션 `질문 대기`, 인스펙터 카드·채팅 인라인·배지 표시 | `답변을 기다리는 질문이 있습니다.` |
| 질문에 답변함 | 답변을 세션에 전달, 카드·인라인 갱신, 세션 재개 | 없음 |
| 질문 대기 중 세션이 삭제됨 | 질문 취소, 활성 카드 제거, 채팅 기록 유지 | `세션이 종료되어 질문이 취소되었습니다.` |
| 에이전트 메시지 수신 세션이 비활성 | 세션 자동 재개 후 전달 | 없음 |
| 에이전트 메시지 수신 세션 자동 재개 실패 | 메시지 보관, 보낸 세션에 실패 알림 | `받는 세션을 재개하지 못했습니다. 메시지를 보관했습니다.` |
| 에이전트 메시지 수신 세션이 삭제됨 | 전달하지 않음, 보낸 세션에 실패 알림 | `받는 세션이 없어 메시지를 전달하지 못했습니다.` |
| `@` 프로젝트가 없음 | 만들지 않음, 전송 막음 | `프로젝트를 찾을 수 없습니다.` |
| `@` 워크트리·브랜치가 없음 | 확인 팝업, 확인 시 브랜치·워크트리 생성 | `이 브랜치의 워크트리가 없습니다. 브랜치와 워크트리를 만들까요?` |
| 워크트리 생성 확인을 취소함 | 태그를 해석하지 못한 상태로 두고 전송 막음 | `참조를 해석하지 못했습니다.` |
| 워크트리 생성이 실패함 | 태그를 해석하지 못한 상태로 두고 전송 막음 | `워크트리를 만들지 못했습니다. 다시 시도해 주세요.` |
| `@` 파일·폴더가 없음 | 만들지 않음, 전송 막음 | `파일 또는 폴더를 찾을 수 없습니다.` |
| 해석하지 못한 태그가 남아 있음 | 전송 버튼 비활성 | `해석하지 못한 참조가 있습니다. 참조를 확인한 뒤 전송해 주세요.` |
| TODO를 불러오지 못함 | 마지막으로 읽은 목록 유지, 오류 표시 | `TODO를 불러오지 못했습니다.` |
| 하네스 패키지가 없거나 버전이 다름 | Goal·List·Loop·Audit·TODO·에이전트 대화·질문 비활성, 안내 | `Pi 하네스 패키지가 없어 Goal·List·Loop·Audit·TODO·에이전트 대화·질문을 사용할 수 없습니다.` |

## 데이터

### 그룹

- 기존 그룹 데이터에 프리셋 필드를 추가하지 않는다.
- 허브 세션(`hubSessionId`)과 부모 저장소(`parentRepo`)는 기존 규칙을 따른다.
- 프리셋 지시는 그룹 생성 시 허브 세션의 초기 컨텍스트로만 전달한다.

### 아카이브

- 별도 엔티티가 아니라 `archivedAt`이 있는 Goal·Audit 조회다. 완료·중단된 Goal과 그 Audit 이력을 모두 보관한다.
- 아카이브는 `groupId`로 조회하고, 세션을 삭제해도 그룹 아카이브의 기록은 유지한다.
- 아카이브에는 목표, 최종 상태, 완료 조건 결과, Audit verdict, 소요 시간, 감사 세션 채팅·증거 링크를 남긴다.

### @참조

- @참조는 별도 엔티티로 저장하지 않는다. 메시지에 태그 텍스트가 남고, 전송 시 해석한 대상 정보가 세션 프롬프트에 함께 들어간다.
- 해석 결과는 레포지토리, 브랜치, 워크트리, 파일·폴더 경로 중 해당하는 값이다.

## 확정된 결정

| 항목 | 결정 |
| --- | --- |
| 문서 위치 | `docs/30-specs/SPEC-hub-orchestration.md` 새 문서. 기존 ADE 명세는 화면·세션 열람 명세로 유지하고 링크한다. |
| 프리셋 저장 | 저장하지 않는다. 생성 시 허브 초기 컨텍스트로만 쓴다. |
| 첫 프롬프트 | Feature·Loop 필수, Manual 선택. 프리셋별 플레이스홀더를 둔다. |
| 허브 권한 | 그룹 안의 워크트리·세션 생성·관리, 프롬프트 전송, TODO 관리. 그룹 생성·삭제·필드 편집은 제외. |
| 허브 확인 | 허브의 관리 조작에는 사용자 확인을 받지 않는다. |
| TODO 범위 | 그룹 TODO + 세션 TODO. 그룹 TODO는 모든 세션이 읽고, 세션 TODO는 그 세션과 허브만 읽는다. |
| TODO 앱 조작 | 읽기 전용. 추가·수정·완료·삭제는 에이전트만 한다. |
| TODO 상태 | `할 일`, `진행 중`, `완료`. |
| TODO 위치 | 상태보드 우측 인스펙터. |
| 에이전트 대화 범위 | 허브와 하위 세션 사이만. 하위 세션끼리·그룹 전체·사용자 참여는 추후. |
| 에이전트 대화 표시 | 받은 세션과 보낸 세션 채팅 모두에 `에이전트` 라벨로 시간순 표시. |
| 수신 세션 비활성 | 자동 재개 후 전달. 실패하면 보관하고 보낸 세션에 알린다. |
| 에이전트 질문 표시 | 인스펙터 카드 + 채팅 인라인. 보드·사이드바에서 `질문 대기` 강조. |
| 에이전트 질문 대기 | 답변 전까지 세션이 기다린다. 답변 후 이어서 진행한다. |
| Goal·List·Loop·Audit 구현 | 새 하네스에 GLLA와 거의 같은 개념을 직접 구현한다. 기존 GLLA를 연동하지 않는다. |
| Goal 소유 | 세션 단위. 모든 작업 세션은 활성 Goal 1개와 대기 Goal 큐를 가진다. 허브는 최상위 Goal 1개와 List를 가진다. |
| Goal과 TODO | 별도 개념. Goal은 완료 조건을 가진 결과, TODO는 실행 작업 목록. 자동 동기화하지 않는다. |
| Goal 상태 | `active`, `auditing`, `complete`, `paused`, `aborted`. `complete`는 Audit 승인으로만 된다. |
| Goal 완료 조건 | 1개 이상. 각 조건은 증거와 함께 Audit에서 통과/실패를 판정한다. 조건 변경 시 revision을 올린다. |
| List 범위 | 세션별 Goal 큐. 세션 List 항목은 Goal이며, 세션은 활성 Goal 1개와 대기 항목을 가진다. 허브 List 항목은 별도 규칙을 따른다. |
| List 다음 항목 | Audit 승인 후 자동 활성화. `aborted`는 자동 진행하지 않고 List를 멈춘다. |
| 허브 List | 오케스트레이션 큐. 항목 자체는 Goal이 아니며, 한 항목을 여러 하위 세션에 fan-out하고 하위 List에 Goal을 넣는다. |
| 허브 다음 항목 | 현재 항목의 유효 하위 Goal이 모두 승인되어야 다음 항목을 배정한다. 대체되지 않은 `aborted`가 있으면 차단한다. |
| 부모 링크 | 하위 Goal은 허브 List 항목 ID를 저장하고, 허브 Audit은 하위 verdict를 롤업한다. |
| 허브 감독 | 허브도 Goal·List·Loop·Audit을 갖고, 직접 구현이 아니라 하위 세션 Goal을 오케스트레이션해 완료한다. |
| Loop 정의 | Goal 하나를 측정값 또는 Audit 기준으로 반복하는 실행 단위. 회차는 1회 반복, 주기는 허브가 항목을 통합하고 다음 항목으로 넘어가는 단위. |
| Loop 측정 | 측정값은 선택. 없으면 Audit 승인만 품질 기준으로 쓰고 상한은 적용한다. 측정값은 하네스가 기록한다. |
| Loop 종료 | 측정 목표 달성·Audit 승인·최대 회차/시간/토큰·중지. 거부 시 상한 내 계속, 상한 소진 시 Loop `stopped`·Goal `paused`(`loop_bounds`). |
| Audit 주체 | 완료 주장 시 작업 세션과 분리된 새 Audit 세션이 수행한다. |
| Audit 범위 | 대상과 같은 워크트리를 읽기 전용으로 검사한다. 소스·설정·의존성을 수정하는 쓰기 도구는 비활성이고, 테스트·측정 명령은 실행할 수 있다. |
| Audit verdict | `approved`, `rejected`, `impossible`, `error`. error는 verdict가 아니라 인프라 실패다. |
| Audit 결과 처리 | 승인→complete, 거부→active+실패 조건, 불가능→aborted, 오류→paused. 허브 Goal 거부 시 보완 항목을 만들어 계속한다. |
| Audit 표시 | 보드·사이드바에 임시 Audit 카드, verdict 후 이력으로 이동. 최신 결과+이력+아카이브. |
| 아카이브 | 완료·중단 Goal과 Audit 이력을 모두 보관하고 그룹 단위로 조회한다. 세션 삭제 후에도 유지한다. |
| 인스펙터 | Goal·List·Loop·Audit 4탭. 그룹은 허브 4탭+하위 집계, 세션은 그 세션 4탭. 읽기 전용. |
| 사용자 제어 | 앱은 읽기 전용. 시작·중지·재시도·재배정·검증은 Pi 채팅이나 에이전트 도구로 한다. 앱에 조작 버튼을 두지 않는다. |
| 보드 배지 | 4슬롯 고정. 강조는 감사 거부·불가능·오류 > 일시정지·차단 > 질문 대기 > 진행·감사 중 > 완료 > idle. |
| Loop 통합 | 각 유효 하위 Goal 승인 시 허브가 통합하고, 현재 항목의 유효 하위 Goal이 모두 승인되어야 다음 항목을 배정한다. 통합의 git 의미는 미정. |
| Run 용어 | 기존 오케스트레이션 Run의 `goal`은 화면에서 `목적`으로 표기한다. |
| @ 대상 | 프로젝트, 브랜치, 워크트리, 파일, 폴더. 파일·폴더는 워크트리 참조 뒤에서만. |
| @ 없는 워크트리 | 확인 팝업 후 브랜치·워크트리 생성. 취소·실패 시 전송을 막는다. |
| @ 없는 프로젝트·파일·폴더 | 만들지 않고 오류로 처리한다. |
| 하네스 패키지 | 이 저장소의 워크스페이스 패키지. 앱이 설치·실행을 관리하고, 배포는 나중에 분리할 수 있다. |

이 표는 사용자 답변을 정리한 것이다. 답변에 없는 구현 세부는 확정으로 올리지 않고 미정사항에 둔다.

### 설계 해석

아래는 사용자 답변을 구현 가능한 형태로 풀어낸 해석이다. 새 제품 결정이 아니라, 답변 사이의 충돌을 없애기 위한 최소 규칙이다.

- **허브 List 항목은 Goal이 아니다.** 허브 Goal 하나가 List 전체를 소유한다. 세션 List 항목만 Goal이다. 이 해석은 "List 항목 = Goal" 답변을 세션 List에 적용하고, 허브는 오케스트레이션 큐로 분리한 것이다.
- **허브 Audit은 롤업 감사다.** 하위 코드를 처음부터 다시 감사하지 않고, 하위 verdict·증거 요약·통합 기록·원래 목표 매핑을 검사한다. 하위 승인이 하나라도 빠지면 허브 Goal을 승인하지 않는다.
- **허브 항목의 유효 하위 Goal 집합은 배정 완료 시점에 고정한다.** 재시도로 대체된 Goal은 `supersededByGoalId`로 빼고, 완료된 항목은 나중 revision 변경으로 되돌리지 않는다. 하위 Goal이 0개인 항목은 완료될 수 없다.
- **Loop의 `paused`와 `stopped`를 구분한다.** 측정 목표 달성·감사 대기는 `paused`(`pauseKind=audit`), 상한·불가능·사용자 중지는 `stopped`다. 상한으로 멈추면 Goal도 `paused`(`loop_bounds`)로 두어 진행 중처럼 보이지 않게 한다.
- **감사 중에는 작업을 멈춘다.** Goal이 `auditing`이면 소유 세션은 새 작업을 시작하지 않는다. Audit은 시작 시 커밋 해시를 고정하고, 그 사이 워크트리가 바뀌면 verdict 없이 `error`로 끝낸다.
- **감사 명령은 읽기 전용 검사로 제한한다.** 테스트·측정 명령은 실행할 수 있지만 소스·설정·의존성 수정은 금지하고, 산출물은 증거로만 쓴다.
- **허브 Audit 거부는 보완 항목으로 푼다.** 허브 Goal은 `active`로 돌아가고, 거부된 완료 조건을 다루는 항목을 허브 List에 추가한다. 허브 Goal 불가능은 그룹 차단이다.
- **`paused`에는 사유가 있다.** 사용자 중지, 감사 오류, 질문 대기, Loop 상한, 의존성, 대기를 구분해 앱에 표시한다.

## 완료 조건

완료 조건은 두 종류다. `[보장]`은 앱·하네스가 코드로 보장하는 조건이고, `[시나리오]`는 허브(LLM)가 프리셋 지시를 따르는지 목업·실행으로 확인하는 조건이다. `[시나리오]`는 결정적 보장이 아니며, 실패하면 프리셋 지시를 보강한다.

- [ ] [보장] Feature·Loop 그룹 생성 화면에서 첫 프롬프트가 비어 있으면 생성 버튼이 비활성이고, Manual은 비워도 생성된다.
- [ ] [보장] 그룹을 만들면 허브 세션 1개와 워크트리 0개가 생기고, 프리셋 지시가 허브 초기 컨텍스트로 전달된다.
- [ ] [시나리오] Feature 그룹에서 허브가 사용자에게 명세 질문을 보내고, 답변 전에는 그 작업의 워크트리를 만들지 않는다.
- [ ] [시나리오] 명세 답변 후 백엔드·프론트엔드 워크트리와 세션이 생기고, 프론트엔드 세션의 목업 선택 질문이 앱에 표시된다.
- [ ] [보장] 목업 선택 질문을 받은 세션이 `질문 대기`로 강조되고, 사용자가 시안을 고르면 답이 그 세션에 전달되어 재개된다.
- [ ] [시나리오] 프론트엔드가 API를 요청하면 허브를 통해 백엔드 API 정보가 전달되고, 그 메시지가 프론트엔드와 허브 채팅에 `에이전트` 라벨로 남는다.
- [ ] [시나리오] Loop 그룹에서 프론트엔드·백엔드 × perf·security·architecture 워크트리와 세션이 생기고, 각 loop 종료 후 허브의 통합 기록이 남는다.
- [ ] [시나리오] Manual 그룹은 프리셋 지시 없이 허브가 구조를 정하고, 첫 프롬프트가 없으면 입력을 기다린다.
- [ ] [보장] 하네스 TODO 도구로 그룹 TODO와 세션 TODO를 만들고 상태를 `할 일`·`진행 중`·`완료`로 바꾸면 인스펙터에 읽기 전용으로 표시된다.
- [ ] [보장] 인스펙터의 TODO에 추가·수정·완료·삭제 버튼이 없고, 앱에서 상태를 바꿀 수 없다.
- [ ] [보장] 세션 TODO는 그 세션과 허브에서만 보이고, 그룹 TODO는 그룹의 모든 세션에서 보인다.
- [ ] [보장] 에이전트 질문이 오면 인스펙터 카드와 채팅 인라인에 동시에 표시되고, 보드 카드·사이드바 세션 행이 강조된다.
- [ ] [보장] 답변 전까지 세션이 대기하고, 답변 후 이어서 진행한다. 앱을 다시 열어도 답하지 않은 질문과 강조가 유지된다.
- [ ] [보장] 에이전트 메시지가 받은 세션과 보낸 세션 채팅 모두에 표시되고, 받는 세션이 비활성이면 자동 재개 후 전달된다.
- [ ] [보장] 자동 재개에 실패하면 메시지가 보관되고 보낸 세션에 실패가 표시된다.
- [ ] [보장] `@backend`를 입력하면 프로젝트·브런치·워크트리 후보가 뜨고, 워크트리가 없으면 확인 팝업 후 브랜치와 워크트리가 생성된다.
- [ ] [보장] 워크트리 참조 뒤 `/`를 입력하면 그 워크트리의 파일·폴더 자동완성이 뜨고, 없는 파일·폴더는 생성되지 않는다.
- [ ] [보장] 해석하지 못한 태그가 있으면 전송이 막히고, 태그를 고친 뒤에만 전송된다.
- [ ] [보장] @참조를 포함한 메시지를 보내면 대상의 레포지토리·브랜치·워크트리·경로 정보가 세션 프롬프트에 전달된다.
- [ ] [보장] 하네스 패키지가 없거나 버전이 맞지 않으면 앱이 안내하고 Goal·List·Loop·Audit·TODO·에이전트 대화·질문 기능을 비활성화한다.
- [ ] [보장] 허브가 요청한 워크트리·세션 삭제와 이름 변경이 사용자 확인 없이 실행되고 보드에 반영된다.
- [ ] [보장] Goal은 완료 조건이 하나 이상 있어야 만들어지고, 완료 조건이 바뀌면 revision이 올라가 이전 Audit 승인이 무효가 된다.
- [ ] [보장] 허브 List 항목에 하위 Goal이 0개면 완료되지 않고 차단으로 표시된다.
- [ ] [보장] 허브 항목의 `childGoalIds`는 배정 완료 시 고정되고, `supersededByGoalId`로 대체된 Goal은 유효 집합에서 빠지며, 완료 후 revision 변경은 완료를 되돌리지 않는다.
- [ ] [보장] Goal은 Audit 승인으로만 `complete`가 되고, 승인 없는 Goal은 List 다음 항목을 활성화하지 않는다.
- [ ] [보장] Goal 완료를 주장하면 Audit 세션이 만들어지고, 보드·사이드바에 임시 Audit 카드가 표시된다. verdict 후 카드는 이력으로 이동한다.
- [ ] [보장] Audit 세션은 읽기 전용이며 쓰기 도구 호출이 거부된다. 테스트·측정 명령은 실행할 수 있고, 감사 중 워크트리가 바뀌면 verdict 없이 `error`로 끝난다.
- [ ] [보장] Goal이 `auditing`이면 소유 세션의 새 작업이 거부되고, Audit은 시작 시 커밋 해시를 고정한다.
- [ ] [보장] Audit 거부 시 Goal이 `active`로 돌아가 실패 조건이 표시되고, 상한이 남은 Loop는 계속된다.
- [ ] [보장] Audit 불가능은 Goal `aborted`, 감사 오류는 Goal `paused`로 표시된다.
- [ ] [보장] 세션 List는 Audit 승인 후 다음 항목을 자동 활성화하고, `aborted`가 나오면 자동 진행을 멈춘다.
- [ ] [보장] 허브 List 항목 하나가 여러 하위 Goal로 fan-out되고, 유효 하위 Goal이 모두 승인되어야 다음 항목이 배정된다. 대체되지 않은 `aborted`가 있으면 차단된다.
- [ ] [보장] 하위 Goal에 부모 허브 항목 ID가 남고, 허브 Audit 탭에 하위 verdict 롤업이 표시된다.
- [ ] [보장] Loop는 측정값·회차·상한·종료 이유를 표시하고, 측정값이 없으면 Audit 승인을 종료 조건으로 쓴다.
- [ ] [보장] Loop 측정 목표 도달 시 `paused`(`audit`)로 두고 Audit 승인 후 `done`이 되며, 상한 도달 시 `stopped`와 Goal `paused`(`loop_bounds`)로 표시된다.
- [ ] [보장] Loop 없는 Goal은 Audit 거부 후 작업·증거 갱신 없이 다시 완료를 주장할 수 없다.
- [ ] [보장] 허브 Goal Audit 거부 시 보완 항목이 생성되고, 허브 Goal 불가능은 그룹 차단으로 표시된다.
- [ ] [보장] `paused` Goal은 사용자 중지·감사 오류·질문 대기·Loop 상한·의존성·대기 사유를 표시한다.
- [ ] [보장] 완료·중단 Goal과 Audit 이력이 아카이브에 남고, 세션을 삭제해도 그룹 아카이브에서 조회된다.
- [ ] [보장] 보드 카드·사이드바에 Goal·Loop·Audit·List 4슬롯 배지가 항상 표시되고, 강조는 문제 우선순위를 따른다.
- [ ] [보장] 그룹 인스펙터에서 허브 4탭과 하위 세션 집계를 함께 보고, 세션 인스펙터에서 그 세션 4탭을 본다.
- [ ] [보장] 오케스트레이션 Run의 `goal`은 화면에서 `목적`으로 표시된다.
- [ ] [시나리오] Feature 그룹의 하위 Goal이 각각 Audit을 거치고, 허브가 하위 verdict를 롤업해 자신의 Goal을 감사한다.
- [ ] [시나리오] Loop 그룹의 6개 하위 Goal이 생성되고, 허브가 현재 항목의 유효 하위 Goal 승인 후 다음 항목을 배정한다.
