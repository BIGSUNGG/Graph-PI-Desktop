## Audit 구조 재정의와 상위 세션 Audit

### 목표

목업에서 상태·오류 전용 화면과 독립 Audit 세션 카드를 제거한다. Audit을 세션 Audit·상위 세션 Audit·그룹 Audit으로 나누고, 자식 Goal이 있는 세션과 그룹 Goal은 직계 자식 Goal의 Audit이 모두 승인·생략된 뒤 상위/그룹 Audit을 시작하며, 감사 에이전트가 생략할 수 있게 한다.

### 확정한 결정

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| Audit 종류 | 세션 Audit·상위 세션 Audit·그룹 Audit | 자식 없는 세션은 자기 작업만, 자식 있는 세션과 그룹은 자기 작업+직계 자식 결과를 통합 검사한다 |
| 세션 Audit 위치 | 해당 세션 인스펙터의 Audit 탭 | 작업 범위를 그 세션으로 한정한다 |
| 그룹 Audit 위치 | 허브 인스펙터의 Audit 탭 | 그룹 전체 결과를 한 곳에서 판정한다 |
| 그룹 Audit 대상 | 그룹 Goal이 만든 세션에서 진행된 Goal만 | 그룹이 만들지 않은 Goal은 통합 감사와 무관하다 |
| 그룹 Audit 없음 | 대상 Goal이 하나도 없으면 실행하지 않음 | 통합할 그룹 작업이 없는데 감사를 만들지 않는다 |
| 상위 세션 Audit 시작 조건 | 직계 자식 Goal이 모두 complete이고 최신 Audit이 `approved` 또는 `skipped` | 자식 Audit이 하위 계층을 정산하므로 부모는 직계 자식만 확인한다 |
| 그룹 Audit 시작 조건 | 그룹 Goal이 만든 세션의 직계 하위 Goal Audit이 모두 `approved` 또는 `skipped` | 상위 Audit 레코드를 별도 조건으로 나열하지 않고 직계 자식 settled만 확인한다 |
| 다단계 Goal | `parentGoalId`로 Goal→Goal→Goal 지원, 순환 금지 | 3단계 예시 `hub → web → qa`로 재귀를 확인한다 |
| 상위 Audit 라벨 | 비허브 상위 세션은 `상위 세션 Audit` | 허브의 `그룹 Audit`과 구분한다 |
| 상위 세션·그룹 Audit 생략 | 감사 에이전트가 판단하며, 생략 시 부모 Goal `complete` | 통합 감사가 불필요한 경우에도 완료를 막지 않는다 |
| 생략 표시 | `통합 감사 생략` 카드에 사유·시각·판단 주체 | verdict와 생략을 구분한다 |
| 보드 표시 | 독립 Audit 카드·노드 없음 | Audit은 세션/허브 Audit 탭과 이력에만 둔다 |
| 상태·오류 화면 | 화면·데이터·검증·증거 모두 제거 | 사용자가 전용 창을 원하지 않았다 |
| 예시 그룹 | `g-feature`를 완료 예시로 사용 | 그룹 생성 세션의 승인 후 그룹 Audit 생략 장면을 보여준다 |

- ADR-0005를 따로 만들었지만 사용자 선택으로 ADR-0004에 합치고 파일을 삭제했다. ADR 번호는 0004까지만 쓴다.

- 2단계 착수 때 ADR-0001·ADR-0002의 supersede 여부와 대체 ADR 번호를 정한다. 지금은 두 ADR 본문을 수정하지 않았다.

### 확인한 사실

- `pi` 는 유효한 에이전트 id이고 기본 설정에서 **터미널 표면**으로 뜼다. 채팅 표면(`--surface chat`)은 확인하지 않았다.
- **세션 JSONL 파일은 첫 턴 전에는 보이지 않았다.** 실행 08:37:14Z, 파일명 시각 08:37:17Z, 파일 mtime 08:37:51Z(첫 프롬프트 전송 이후). 즉 보드에 새 세션이 나타나는 시점은 첫 프롬프트 이후다.
- `terminal send` 는 `provider: unsupported` 로 전달을 관측하지 못한다. 앱은 전송 성공을 화면 출력이나 세션 파일 증가로 판정해야 한다(SPEC §3.5의 전송 중·전송됨 표시 근거).

## MVP 구현 계획

**상태: 제안 · 구현 미승인.** 아래 단계는 구현 순서이며 범위를 줄이는 분할 출시안이 아니다. 앱과 하네스는 [[SPEC-graph-pi-ade]] 및 [[SPEC-hub-orchestration]]의 포함 범위 전체를 구현한다. 완료는 [[SPEC-mvp-acceptance]]의 **64행(보장 57 + 시나리오 7)**으로 판단한다. 원격 접속 구현·Orca 전면 제거·Pi 런타임 포크는 제외한다([[ADR-0005-mvp-scope-both-specs-and-remote-access]], [[ADR-0004-orca-removal-then-pi-runtime-fork]]).

### 출발점

- `b75c324` 기준 `mock/index.html`과 검증 스크립트가 있고 `out/`의 Electron 번들은 추적되지만, 앱 소스 `src/`와 루트 manifest·lockfile·electron-vite/TypeScript 설정은 없다. 첫 작업은 **소스를 확보할 수 있는지 확인하고 재현 가능한 빌드를 마련하는 것**이다. 확보할 원본이 없으면 새 최소 뼈대의 변경 범위를 승인받는다. 기존 `out/`·`dist/`의 정리 여부는 이 계획에서 결정하지 않는다.
- `mock/COVERAGE.md`는 `b56ea90`의 47행에서 세션 계보가 추가된 `75e0dc3`의 51행으로 늘었다. 현재 51개 목업 장면은 UI 대조 자료이고, 64개 앱 판정과는 다른 수다. 장면별 사용자 확인 이력과 전체 매핑은 이번에 재검증하지 않았다. 변경된 화면은 `mock/`의 확인 가능한 장면을 먼저 대조하고, 사용자 확인을 받은 뒤 제품 코드를 바꾼다.
- 이전 실측으로 **Orca가 Pi PTY를 띄울 수 있다**는 점은 확인됐다(이 일지의 `MVP 착수 전 확인` 절). 첫 프롬프트 뒤 JSONL이 생겼다는 단일 관찰은 아직 PTY↔Pi 세션 식별이나 재개가 항상 된다는 근거가 아니다.

### 모듈·API 경계 초안

경로와 API 이름은 설계 검토용이며 현재 존재하는 코드가 아니다. 별도 서버나 네트워크 transport는 만들지 않는다.

| 모듈 | 책임과 호출 경계 |
| --- | --- |
| `electron.vite.config.ts`, `src/main/index.ts`, `src/preload/index.ts` | 앱·창 수명주기와 IPC 등록. preload는 `contextIsolation`을 켠 상태에서 명시된 메서드만 노출하고 Node나 범용 IPC 호출을 노출하지 않는다. |
| `src/shared/contract.ts` (경로 제안) | `listSessions(groupId)`, `getSession(sessionId)`, `searchHistory(query)`, `sendPrompt(sessionId, input)`, `answerQuestion(questionId, answer)`처럼 용도별 요청·결과 규격을 담는다. main이 실제 대상을 확인하고, renderer는 로컬 경로·PTY 핸들·명령줄을 직접 고르지 않는다. |
| `src/main/orca/`, `src/main/pi/` | Orca는 PTY·워크트리/프로젝트 조작과 읽기 조회, Pi 어댑터는 원본 JSONL 헤더·메시지·계보의 증분 읽기. 예: `agent launch` 수신 결과에서 터미널 핸들을 확인 → `terminal send --terminal <handle> --text <prompt> --enter` → 바인딩된 Pi ID의 JSONL에서 반영 관찰. CLI 종료 코드와 JSON `ok`를 모두 검사하고, Run 하위 조회에는 `--run`을 넣는다. 실측/광고 명령 구분은 [[orca-cli-and-pi-sessions]] 참조. |
| `src/main/db/`, `src/renderer/` | DB는 앱의 파생 검색 인덱스, Pi JSONL은 원본이다. renderer는 계약을 통해 받은 상태로 화면·선택·오류를 표시한다. Goal·List·Loop·Audit·TODO 상태 변경 API를 화면에 노출하지 않으며, 사용자 질문 답변은 별도 경로다. |
| 저장소 내 Pi 하네스 패키지와 main 연결부(경로 미정) | 하네스가 작업 상태와 전이를 소유하고 main은 버전 호환성을 검사해 앱에 읽기 모델을 제공한다. `하네스 → 실행 요청 → main/Orca → Pi` 채널의 세션 식별·권한·실행 결과, 전이의 단일 기록 주체, 동시 쓰기·재시작 복구는 0단계 설계에서 확정한다. |

### 승인·검증이 필요한 항목

| 언제 | 미정 항목 또는 실측 과제 |
| --- | --- |
| **0단계 착수 전** | 소스 확보/뼈대 범위, 검증 플랫폼·Orca/Pi 버전과 임시 저장소, 실제 모델 실행의 자격 증명·비용 한도. |
| **해당 보드·인스펙터 구현 전** | 판정표 #6/#33의 세션 상세 배치와 #5/#14의 첫 턴 전 표시 정책을 선택하고 해당 목업을 확인한다. |
| **0단계에서 확인, 하네스 구현 전 승인** | 같은 cwd의 복수 세션에서 PTY→Pi ID를 확실히 식별하는 방법, 워크트리 카드 밖 허브 생성/재개, 그룹 권한의 실제 집행. Pi 확장으로 로딩·도구 제한·`auditing` 중 새 작업 차단·회차 훅·시간/토큰 사용량 관찰·감사 세션 실행이 되는지 검증한다. 안 되는 기능을 포크나 우회 구현으로 임의 확장하지 않는다. 하네스 이름/경로/배포·상태 스키마·Pi 명령 표면·Goal 생성 권한도 이때 확정한다. |
| **허브의 쓰기 동작 전** | Git 통합의 의미(대상·순서·충돌·push), 미커밋 삭제 권한, 하위 세션 보존, 사용자 수동 조작과 허브 충돌 처리, 작명과 동시 상한. 명세의 허용 범위를 넘는 Git 동작을 기본값으로 넣지 않는다. |
| **Audit 구현 전** | #38과 #47–48의 `skipped`가 Goal 완료·List 전진·상위 gate에서 각각 어떤 의미인지 확정. 권한 차단의 위협 모델, 작업 에이전트의 상태·verdict 위조 방지 경계, 감사 대상의 고정 범위와 산출물 격리, 검사 명령 허용 범위를 정한다. 모델·상한·timeout·오류 복구·보완 항목·증거 마스킹/아카이브 정책은 [[SPEC-hub-orchestration#미정사항]]에 맞춰 확인한다. |
| **Loop·프리셋 구현 전** | 측정 명령 안전 정책, 회차·시간·토큰 한도, 정체·중지·재배정과 그룹 주기 종료 조건, 프리셋 지시 노출·카피 확정. 실제 모델 시나리오는 재현 입력·모델/설정·관찰 순서·스모크 실행 비용이 승인된 뒤 거친다. |

실험 실패는 통과로 기록하지 않는다. 세션 대상이 모호하면 제어를 유효하다고 가정하지 않고, 감사에서 허용된 명령으로도 원본 쓰기를 막을 수 없다면 읽기 전용이 검증될 때까지 #50을 미완료로 둔다. 확정되지 않은 정책은 해당 단계 설계에서 사용자에게 확인한다.

### 최종 검증 기록 방식

- #1–57은 상태 전이·파싱·권한 등의 자동 테스트와 실제 Electron/Orca/Pi 행동 확인을 조합한다. #58–64는 목업과 대조하되 실제 모델 동작과 근거를 별도로 남긴다. fixture·모의 verdict는 런타임 증거가 아니다.
- 확인된 행만 판정표와 원본 SPEC에 함께 체크하고, 각 행에 명령 또는 재현 동작과 결과를 일지로 연결한다. 현재는 어떤 행도 이번 계획 작업을 근거로 체크하지 않았다.
- 이번 작업의 검증: `git diff --check` 통과. Node 문서 검사에서 단계별 #1–64 대응(중복·누락 없음), 보장 57·시나리오 7, 계획 위키링크 8개와 worklog 색인을 확인했다. `node mock/_check.js` → `PASS ids=60 sessions=35 worktrees=22 tasks=19 workers=12`(목업 내부 정합성). 앱 빌드·실행, 브라우저 목업 재검증, 새 Orca/Pi 연동 검증은 실행하지 않았다.
