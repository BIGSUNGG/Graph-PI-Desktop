# ADR-0005 MVP 범위는 두 SPEC 전체이고 원격 접속은 구조만 열어둔다

- 한 줄 요약: MVP는 [[SPEC-graph-pi-ade]] 와 [[SPEC-hub-orchestration]] 범위 전체(목업 47장면)이고, 원격 접속은 MVP에서 구현하지 않되 스택은 이후 원격을 붙일 수 있는 구조를 전제로 정한다.
- 상태: active
- 날짜: 2026-11-22

## 맥락

[[ADR-0004-orca-removal-then-pi-runtime-fork]] 는 MVP 범위를 [[SPEC-graph-pi-ade]] 로 한정했다. 그런데 그 명세 §6.2가 프리셋별 첫 프롬프트와 생성 후 허브 동작을 [[SPEC-hub-orchestration]] 에서 확정하도록 넘기고, 목업 `mock/COVERAGE.md` 는 두 명세를 합친 47장면을 검증한다. 사용자는 2026-11-22에 MVP 범위를 두 명세 전체로 답했다. 같은 답에서 다른 기기나 웹에서 Graph PI 화면을 원격으로 보거나 조종하는 요구가 함께 나왔다.

## 결정

1. **MVP 범위는 두 SPEC의 포함 범위 전체다.** [[SPEC-graph-pi-ade]] 와 [[SPEC-hub-orchestration]] 을 모두 대상으로 하고, 사용자 가시 범위의 기준은 `mock/COVERAGE.md` 의 47장면이다.
2. **원격 접속은 MVP에서 구현하지 않고 구조만 열어둔다.** 다른 기기나 웹에서 같은 화면을 열람·조종하는 기능은 MVP 이후에 만들고, MVP에서는 그 기능을 붙일 수 있도록 스택과 프로세스 경계를 정한다.
3. 이 ADR은 [[ADR-0004-orca-removal-then-pi-runtime-fork]] 의 "MVP 범위는 SPEC-graph-pi-ade" 문장만 대체한다. 3단계 로드맵(Orca 전면 제거 → 업스트림 Pi 런타임 포크)과 어댑터 도입·업데이트 수용 결정은 그대로 유효하다.

## 해석이 들어간 곳

- 원격 접속은 2026-11-22 사용자 답으로 "MVP에서는 구현 안 함, 구조만 열어둠"으로 확정됐다. 대상 기기, 열람·조종 범위, 인증·보안 방식은 원격 기능을 명세할 때 정한다.
- 47장면을 MVP 기준으로 삼는 것은 사용자 답 'graph + hub 전체(47장면)'에서 온 것이다. 장면별 우선순위는 정해지지 않았다.

## 대안

아래 대안은 작성 에이전트가 구성했고 사용자는 검토하지 않았다. 사용자는 2026-11-22에 범위를 직접 지정했다.

| 대안 | 장점 | 단점 | 판정 |
| --- | --- | --- | --- |
| [[SPEC-graph-pi-ade]] 범위만 | MVP 기간이 짧고 완료 판정이 명확하다 | 허브·감독 기능이 뒤로 밀리고, 그 명세가 허브 동작을 다른 명세로 넘겨 그룹 흐름이 미완으로 남는다 | 제외(사용자 선택) |
| graph + 허브 기본 흐름만 | 자율 관리 흐름까지 확보한다 | 감독 탭·에이전트 질문·`@`참조가 빠져 목업 47장면과 어긋난다 | 제외(사용자 선택) |
| **두 SPEC 전체** | 목업·완료 조건·구현 범위가 일치한다 | MVP 기간이 가장 길다 | 선택 |

## 결과

- MVP 완료 판정은 두 명세의 완료 조건을 합쳐서 본다. [[SPEC-graph-pi-ade]] 의 19개는 그중 일부다.
- 원격 접속은 아직 명세에 없고 MVP 구현 범위도 아니다. 스택 결정에서는 이후 원격을 붙일 수 있는 프로세스 경계(로컬 데스크톱 앱 단독인지, 앱 + 로컬 서버인지)를 함께 본다.
- 단점: 범위가 커져 MVP 기간이 늘고, 원격 전제 때문에 스택 후보가 줄어든다. 원격을 미루면 그만큼 구조를 바꾸는 비용은 뒤로 밀린다.

## 후속 작업

- MVP 완료 판정표는 [[SPEC-mvp-acceptance]] 로 만들었다. 남은 확인 항목(세션 상세 위치, 세션 등장 시점)은 구현 전에 정한다.
- 원격 접속 기능을 명세할 때 범위(열람·조종), 대상 기기, 인증을 정한다. 시점은 MVP 이후다.
- 스택 후보를 원격 전제로 비교해 사용자에게 선택받는다.
