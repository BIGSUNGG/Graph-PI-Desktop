# ADR-0004 MVP는 Orca와 Pi를 병행하고, 이후 Orca를 제거한 뒤 Pi 런타임을 포크한다

- 한 줄 요약: MVP는 [[SPEC-graph-pi-ade]] 범위, 이후 Orca 전면 제거, 그 다음 업스트림 Pi 런타임 포크.
- 상태: active
- 날짜: 2026-11-22

## 맥락 (Context)

[[ADR-0001-standalone-ade-over-orca-plugin]] 은 ADE를 별도 데스크톱 앱으로 만들고 Orca를 엔진으로만 쓰기로 했다. [[ADR-0002-pi-session-jsonl-data-source]] 는 대화는 Pi 세션 JSONL, 제어는 Orca CLI를 쓰는 하이브리드를 골랐다. 두 결정 모두 Orca를 실행 엔진이자 제어 경로로 두는 전제를 갖는다.

2026-11-22 사용자가 장기 방향을 세 단계로 밝혔다.

1. MVP 단계는 Orca와 Pi 하네스를 함께 쓴다(현재 구조 유지).
2. MVP 종료 후에는 **Orca 없이** 기능을 추가 구현한다. Orca가 맡던 범위는 전면 제거한다.
3. 그 이후 **업스트림 Pi 런타임을 포크**해 새 하네스를 만든다.

같은 날 사용자가 세부를 더 답했다. MVP 범위는 `graph-pi-ade` 명세([[SPEC-graph-pi-ade]])이고, Orca가 하던 것은 이 프로젝트가 구현하며, 어댑터를 고려한다. [[SPEC-graph-pi-ade]] 의 완료 조건 체크리스트는 2026-11-22 기준 19개, 모두 미체크다.

## 결정 (Decision)

제품 개발을 위 세 단계 순서로 진행한다. 1단계 동안에는 ADR-0001·ADR-0002가 그대로 유효하다. 2단계에서 Orca 의존을 전면 제거하고, 3단계에서 업스트림 Pi 런타임을 포크해 자체 하네스를 소유한다.

1. **MVP 범위·완료 기준**은 [[SPEC-graph-pi-ade]] 의 포함·제외 범위와 완료 조건 체크리스트다. 19개를 모두 체크하면 MVP 완료로 판정한다(사용자 확인 2026-11-22). MVP용 명세를 따로 만들지 않는다.
2. **Orca가 제공하던 기능은 이 프로젝트가 직접 구현**한다. 대상 기능의 전체 목록은 2단계 설계에서 확정한다. 지금까지 [[SPEC-graph-pi-ade]] 포함 범위에서 확인되는 항목은 워크트리 생성·관리, PTY 터미널, Pi 세션 실행·입력·중단, 오케스트레이션 Run·Task·Worker·Gate 조회다. 위 2단계 문구의 '터미널·에이전트 실행·오케스트레이션 제어'를 명세 문구로 구체화한 것이다.
3. **어댑터 경계를 검토한다.** 목표는 2단계에서 화면·도메인 코드를 고치지 않고 Orca 구현을 자체 구현으로 교체하는 것이다. 도입 여부, 경계의 형태·범위, 적용 시점은 아직 정하지 않았다.

용어: 3단계에서 말하는 'Pi 하네스'는 [[glossary|Pi 하네스 패키지]](이 저장소의 워크스페이스 패키지)가 아니라 업스트림 Pi 런타임을 뜻한다.

### 해석이 들어간 곳

사용자 진술을 넘어 작성자가 읽어 넣은 부분이다. 틀렸으면 이 ADR을 조정한다.

- 외부 엔진·다른 제품에 위임하지 않는다는 것: 사용자 진술 '이 프로젝트에서 구현'에서 읽은 해석이다.
- 어댑터의 목적 진술: 사용자는 '고려'만 말했다. 목적·형태는 작성자 제안이다.

### 이 ADR이 결정하지 않는 것

- 어댑터 도입 여부·형태·적용 시점.
- 1단계에서 어댑터 없이 화면 구조를 어디까지 확정할지.
- 포크할 업스트림 Pi 저장소·버전·업스트림 추적 정책.
- 포크 뒤 Pi 하네스 패키지의 존속 형태.
- 2단계에서 바뀔 Orca 전제 명세 항목(예: Orca 상태 3초 폴링, Orca 미실행 시 제어 비활성).

## 대안 (Alternatives)

아래 대안은 작성 에이전트가 구성했고 사용자는 검토하지 않았다. 사용자는 2026-11-22에 3단계 순서, MVP=SPEC 범위, 자체 구현, 어댑터 고려를 직접 지정했다.

### 단계 구성

| 대안 | 장점 | 단점 | 선택 여부 |
| --- | --- | --- | --- |
| Orca 유지 + Pi 런타임 포크만 | 워크트리·터미널·오케스트레이션 제어를 Orca에 계속 위임하므로 앱이 구현할 범위가 작다 | Orca 실행이 계속 필요하고 CLI 폴링 의존이 남는다(ADR-0001·ADR-0002 기록) | 제외 (사용자 방향) |
| Orca 제거를 MVP보다 먼저 | 마이그레이션을 한 번만 한다 | MVP 일정에 워크트리·터미널·에이전트 실행·오케스트레이션 제어 구현이 선행 조건으로 붙는다 | 제외 (사용자 방향) |
| Pi 런타임 포크를 Orca 제거보다 먼저 | 하네스 소유권을 먼저 확보한다 | Orca 연동과 포크한 런타임을 동시에 관리해야 한다 | 제외 (사용자 방향) |
| 병행 → Orca 전면 제거 → Pi 런타임 포크 | MVP 일정이 현재 구조로 유지되고, 제거와 포크가 한 번에 겹치지 않는다 | 2단계에서 제어 계층을 다시 만들어야 하고, 3단계 세션 포맷·파싱 계층 변경 폭은 아직 모른다 | **선택 (사용자 지정)** |

### 범위·구현 방식

| 대안 | 장점 | 단점 | 선택 여부 |
| --- | --- | --- | --- |
| MVP를 SPEC보다 축소 | 더 빨리 검증한다 | 화면 4종·그룹·허브를 전제로 쌓은 기획([[SPEC-hub-orchestration]], 목업)이 MVP 밖이 되어 판정 기준이 둘로 갈린다 | 제외 (사용자 방향) |
| Orca 기능을 외부 엔진·라이브러리에 위임 | 직접 구현할 양이 줄어든다 | ADR-0001이 플러그인 경로를 제외한 제약(대화 API 부재, 패널 샌드박스)과 같은 문제를 다시 만난다. Orca 제거 목적과도 어긋난다 | 제외 (사용자 방향) |
| 어댑터 없이 화면이 Orca CLI를 직접 호출 | 1단계 코드가 적다 | 2단계에서 화면·도메인 코드를 함께 고쳐야 하고, 3단계 런타임 교체 때 같은 비용을 다시 낸다 | 제외 (사용자 방향) |

## 결과 (Consequences)

- 장점: MVP 완료 여부를 [[SPEC-graph-pi-ade]] 완료 조건 체크리스트로 판정할 수 있다. Orca 의존이 경계 뒤로 모이면 2단계에서 화면을 다시 만들지 않을 수 있다.
- 단점: 2단계 구현 범위가 넓다(워크트리·터미널·세션 실행·오케스트레이션 조회). 어댑터는 검토 단계이므로 비용과 형태가 아직 확정되지 않았다. 3단계에서 세션 포맷과 파싱 계층이 얼마나 바뀌는지는 포크한 런타임이 현재 포맷을 유지할지에 달려 있어 아직 알 수 없다.
- 되돌리기 비용: SPEC 범위를 MVP로 쓰면 완료 조건을 늘리거나 줄이는 것이 곧 MVP 기준 변경이 된다. 2단계를 마친 뒤 Orca 엔진으로 돌아가려면 자체 제어 계층을 버리고 Orca CLI 경로를 다시 연결해야 한다. 3단계 이후 업스트림 Pi로 돌아가려면 포크에서 고친 부분을 업스트림과 다시 합쳐야 한다.

## 후속 작업

- 2단계에서 구현할 Orca 기능 전체 목록을 확정한다. 조회 전용과 실행 포함을 구분한다.
- 어댑터 경계의 도입 여부와 형태(인터페이스 단위, 폴더 위치, 테스트 대역)를 정한다. 이 ADR은 검토 방향만 정했다.
- 어댑터 형태가 정해지기 전에 1단계 화면 구조를 어디까지 확정할지 정한다. 열린 질문이다.
- [[SPEC-graph-pi-ade]] 완료 조건 중 Orca 전제인 항목이 2단계에서 어떻게 바뀌는지 그때 정한다.
- 포크할 업스트림 Pi 저장소·버전과 업스트림 추적 정책, Pi 하네스 패키지의 존속 형태를 정한다.
- 2단계에 들어갈 때 Orca 엔진 전제를 대체하는 ADR을 새 번호로 발급한다. ADR-0001의 '별도 앱' 결정과 ADR-0002의 JSONL 파싱 부분은 Orca 제거 뒤에도 남을 수 있으므로, 0001·0002의 상태는 그 시점에 [[conventions#문서 생애주기]] 규칙으로 정한다.
- 2단계 착수 시 [[SPEC-graph-pi-ade]] · [[SPEC-hub-orchestration]] 의 Orca 전제 조항과 [[orca-cli-and-pi-sessions]] 의 제약 기록을 다시 확인한다.
