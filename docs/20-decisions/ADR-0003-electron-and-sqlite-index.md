# ADR-0003 앱은 Electron + React + TypeScript, 검색 인덱스는 SQLite FTS5로 만든다

- 상태: active
- 날짜: 2026-11-17

## 맥락 (Context)

[[SPEC-graph-pi-ade]] 는 네 화면에서 세 가지 일을 동시에 한다.

1. 로컬 파일(Pi 세션 JSONL 2,272개)을 감시하고 자라는 내용을 읽는다.
2. Orca CLI를 주기적으로 호출하고, 프롬프트는 PTY로 보낸다.
3. 30일 이전 세션까지 본문으로 검색한다.

브라우저에서 돌 수 없는 이유가 1·2에 있다. 파일 경로 접근과 PTY 제어가 필요하므로 데스크톱 런타임이 전제다. 3은 세션 수가 많아 매번 전체 스캔하면 검색이 느려진다.

## 결정 (Decision)

- **앱 스택**: Electron + React + TypeScript. 창·파일 감시·PTY·패키징을 검증된 방식으로 처리하고, Orca 소스의 같은 패턴(파일 감시, 터미널 제어, IPC 경계)을 참고한다.
- **검색 인덱스**: 앱 데이터 폴더의 SQLite 파일 하나에 FTS5 색인을 둔다. 세션 파일이 늘면 증분으로 갱신하고, 원본 JSONL은 읽기만 한다.

## 대안 (Alternatives)

| 대안 | 장점 | 단점 | 선택 여부 |
| --- | --- | --- | --- |
| Electron + React + TS | 파일 감시·PTY·패키징 검증됨, Orca 코드 참고 가능 | 설치 용량·메모리 큼 | **선택** |
| Tauri v2 + React | 번들 작음, 메모리 적음 | PTY·파일 감시·프로세스 제어를 Rust 플러그인으로 직접 구현, Orca 코드 참고 불가 | 제외 |
| 로컬 웹 서버 + 브라우저 | 구현 빠름 | 임의 경로 읽기·터미널 제어 불가로 이 앱의 핵심 기능 불가 | 제외 |
| SQLite FTS5 | 증분 색인, 수천 세션에서도 즉답 | 네이티브 모듈이라 Electron 버전 맞춤 빌드 필요 | **선택** |
| 세션별 JSON 인덱스 | 의존성 없음 | 2,272개 규모에서 검색마다 전체 로드 | 제외 |
| 저장 없이 매번 스캔 | 저장 구조 없음 | 앱 시작·검색마다 전체 파일 스캔 | 제외 |

## 결과 (Consequences)

- 장점: 파일 감시와 PTY 제어를 Electron 기본 모듈로 처리한다. 본문 검색은 인덱스에서 답하므로 화면이 세션 수에 비례해 느려지지 않는다.
- 단점: Electron 네이티브 모듈(sqlite)을 앱 버전과 함께 빌드·배포해야 한다. 인덱스가 원본과 어긋날 수 있어 재생성 경로가 필요하다.
- 되돌리기 비용: 스택 교체는 IPC 경계를 유지하면 UI 계층을 재사용할 수 있지만 패키징·파일 감시 구현은 다시 써야 한다. 인덱스 교체는 검색 계층만 바꾸면 되고, 원본 세션 파일은 손대지 않으므로 데이터 손실은 없다.

## 후속 작업

- 인덱스 스키마(테이블·FTS 컬럼·재생성 조건)는 설계 문서에서 정한다.
- 세션 파일이 삭제·이동된 경우 인덱스 정리 규칙을 정한다.
